Every Azure setup I've worked on eventually hits the same question: how do you keep dev, staging, and production consistent without copy-pasting infrastructure code three times and hoping nobody forgets to update all three copies?

Terraform workspaces are the answer I've settled on, and it's worth explaining why, because the concept is simple but easy to misuse.

## What a workspace actually is

A Terraform workspace lets you use the exact same `.tf` configuration files, but apply them against a separate state file per environment. Same code, different state. That's it.

```bash
terraform workspace new staging
terraform workspace select staging
terraform plan
```

The plan command now only compares against staging's state, not production's. This sounds small, but it's the difference between "I can safely test a change in staging" and "I have to maintain three nearly-identical copies of my Terraform code and hope they don't drift."

## Remote state is not optional

If you're working alone, local state files feel fine, until you're not working alone anymore, or until your laptop dies with the only copy of your production state on it. I set up remote state (in an Azure Storage Account) from the very start, specifically so:

- Multiple people (or future me, on a different machine) can safely run `terraform plan` without stepping on each other
- State is backed up somewhere that isn't a single laptop
- Locking prevents two applies from racing each other

## Where this setup actually gets tested

The real value shows up when something needs to change across all three environments, say, a new subnet or an updated VM size. Because dev, staging, and production are all defined from the same source, I make the change once, plan it against dev first, then staging, then production, in that order. If dev and staging both apply cleanly, production almost always does too, because it's not running different code, just a different state.

```hcl
resource "azurerm_linux_virtual_machine" "app" {
  count               = terraform.workspace == "production" ? 3 : 1
  # sizing and other config shared across environments,
  # only the count differs based on workspace
}
```

## What I'd tell someone starting this today

Don't reach for workspaces if you only have one environment, they're solving a problem you don't have yet. But the moment you have two environments that are supposed to look similar, set up remote state and workspaces before you write much Terraform, not after. Retrofitting this onto an existing pile of copy-pasted `.tf` files is a much bigger job than starting with it.
