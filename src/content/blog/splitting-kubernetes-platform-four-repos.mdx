When I started building CloudBite, my first instinct was the same one most people have: put everything in one repo. The app code, the Terraform, the Helm charts, the CI/CD config, all in one place, one pipeline, one `main` branch to worry about.

It worked for about a week.

The problem showed up the first time I needed to bump a Terraform provider version and didn't want that anywhere near the app's deploy pipeline. Or the time I wanted to update a Helm chart's resource limits without triggering a full CI run of the application tests. Everything was coupled, so everything moved at the speed of the slowest, most cautious change.

So I split it into four repos:

- **Application layer**, the actual service code
- **CI/CD pipelines**, build, test, and deploy logic
- **Terraform infrastructure**, the AKS cluster, networking, everything underneath
- **Helm chart deployments**, how the app actually gets onto the cluster

## Why this actually helps

The biggest win isn't organizational neatness, it's that each repo can have its own release cadence and its own review standards. Infrastructure changes are inherently riskier than a UI tweak, so they deserve more scrutiny and a slower, more deliberate pace. Bundling them together means either your infra changes move too fast, or your app changes move too slow. Neither is good.

It also made security scanning easier to enforce properly. Trivy scans images before they ship, SonarQube gates code quality, and neither of those checks has to know or care about what's happening in the Terraform repo. Each pipeline does one job.

```yaml
# Simplified example: the CI/CD repo's pipeline references
# the other repos as pinned versions, not live branches
stages:
  - scan: trivy image scan
  - quality: sonarqube gate
  - deploy: helm upgrade --install cloudbite ./charts/cloudbite
```

## The tradeoff, honestly

Four repos means four places to keep track of, and coordinating a change that touches more than one of them (say, a new environment variable that needs to exist in both the app and the Helm values) takes a bit more discipline. I keep a short checklist for exactly this kind of cross-repo change so nothing gets missed.

## Would I do it again?

Yes, but I'd split earlier next time. I waited until the single-repo pain was already annoying before I made the change. If a project has more than two genuinely different concerns (app code and infra are the obvious minimum), it's usually worth splitting from day one rather than waiting for the coupling to hurt.
